End-to-End Data Flow & Lifecycle

This manual traces the exact lifecycle of clinical data across the application: from clinician score input on a mobile touchscreen, through mathematical domain calculation, SQLite persistent storage, audit queue logging, background cloud push, and formal PDF generation.

2. Offline-First Cloud Synchronization Pipeline

MotorMeasure Pro implements an autonomous, non-blocking synchronization engine:

Sync Worker LifecycleBackground Thread (60s Loop)

                 v
(1) Connectivity Probe:
    Tries Supabase port 443 -> Fallback ping Google DNS (8.8.8.8:53)
    |-- If OFFLINE: Logs message, sleeps 60s, does NOT attempt network calls.
    |-- If ONLINE : Continues to Step 2.
                 |
                 v
(2) Offline User Provisioning:
    Queries app_users where cloud_uid IS NULL
    |-- If active cloud session matches: Backfills cloud_uid in SQLite
                 |
                 v
(3) Session Authentication Check:
    Verifies valid JWT in Supabase client
    |-- If expired: Attempts silent refresh via ~/.gmfm_app/.cloud_token
                 |
                 v
(4) Push Phase (Local -> Cloud):
    SELECT * FROM sync_queue WHERE synced = 0 ORDER BY id ASC LIMIT 100
    |-- For each mutation (INSERT, UPDATE, DELETE):
    |     Executes client.table(table).upsert(cloud_payload)
    |     UPDATE sync_queue SET synced = 1 WHERE id = ?
                 |
                 v
(5) Pull Phase (Cloud -> Local):
    SELECT * FROM cloud_table WHERE created_by = self._user_id AND updated_at > last_pull
    |-- For each incoming record:
    |     Checks if record has pending local edits in sync_queue!
    |     * IF PENDING LOCAL CHANGE: Skip (Local Wins conflict rule)
    |     * IF NO LOCAL CHANGE     : Upsert into local SQLite
                 |
                 v
(6) Commit Metadata:
    Updates sync_metadata key 'last_pull' with current ISO UTC timestamp.

3. Clinical PDF Generation Pipeline

Exporting an assessment report engages the multi-tier fallback pipeline in ReportService:

  • Stage 1 - Context Resolution: Resolves student record (decrypting PII name and medical record identifier), loads session scores, and looks up the assessor's full name via UserRepository.
  • Stage 2 - Backend Probe:
    1. Checks if reportlab is installed. If yes, builds a styled document flow with embedded Matplotlib trend charts.
    2. If ReportLab is unavailable (common in stripped Android Python environments), lazily imports pure-Python fpdf2.
    3. If fpdf2 is missing, engages the zero-dependency Raw PDF fallback, constructing standard PDF 1.4 byte streams directly.
  • Stage 3 - File Persistence & System Share: Writes the resulting PDF to the application's reports/ directory and triggers native OS viewer intents where supported.

4. Authentication & Role Reconciliation Lifecycle

Authority Boundary
While the local SQLite database manages immediate user authorization offline, Supabase is the ultimate authoritative source of truth for user roles (governed by the PostgreSQL trigger protect_profile_role()).

When an authenticated user signs in:

  1. Local PBKDF2 hash is validated against SQLite app_users table.
  2. Session is stored in Flet's encrypted client storage.
  3. A background thread triggers AuthService._cloud_provision().
  4. Upon successful cloud authentication, the service fetches profiles.role. If an administrator updated the user's role on the cloud console (e.g. promoting a Teacher to Admin), the local database row is reconciled immediately, and an in-app SnackBar notification alerts the user.
