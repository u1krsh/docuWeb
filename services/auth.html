Authentication Service & PBKDF2 Specification

Two-Tier Authentication
MotorMeasure Pro couples local cryptographic verification with asynchronous cloud account provisioning inside src/gmfm_app/services/auth_service.py.
Document Contents

  • 2. Two-Tier Login Lifecycle

1. PBKDF2-HMAC-SHA256 Password Cryptography

Passwords are never stored in plaintext. Local credential verification utilizes PBKDF2 with HMAC-SHA256, configured with 200,000 iterations and a 16-byte cryptographically secure pseudorandom salt generated via os.urandom():

src/gmfm_app/services/auth_service.pyPassword Hashing & Verification
def hash_password(password: str, iterations: int = 200_000) -> str:
    salt = os.urandom(16)
    digest = hashlib.pbkdf2_hmac("sha256", password.encode("utf-8"), salt, iterations)
    salt_b64 = base64.b64encode(salt).decode("utf-8")
    digest_b64 = base64.b64encode(digest).decode("utf-8")
    return f"pbkdf2_sha256${iterations}${salt_b64}${digest_b64}"

def verify_password(password: str, encoded_hash: str) -> bool:
    try:
        algorithm, iterations_raw, salt_b64, digest_b64 = encoded_hash.split("$", 3)
        if algorithm != "pbkdf2_sha256":
            return False
        iterations = int(iterations_raw)
        salt = base64.b64decode(salt_b64)
        expected = base64.b64decode(digest_b64)
        candidate = hashlib.pbkdf2_hmac("sha256", password.encode("utf-8"), salt, iterations)
        # Constant-time comparison prevents timing side-channel attacks
        return hmac.compare_digest(candidate, expected)
    except Exception:
        return False

2. Two-Tier Login Lifecycle

When a user submits credentials in LoginView:

  1. Local Authentication: The username is normalized (stripped and lowercased) and queried from app_users. If found and active, verify_password() runs.
  2. New Device Cloud Fallback: If the username is not found locally but contains an '@' character (an email), and cloud sync is configured, the service attempts to sign in to Supabase. If successful, it automatically provisions the user row in local SQLite!
  3. Session Persistence: User ID and username are stored in Flet's encrypted client_storage.
  4. Asynchronous Cloud Trigger: _cloud_provision() is initiated on a daemon worker thread.

3. Automatic Cloud Provisioning Mechanism

Clinicians do not need to manage separate cloud and local accounts. The _cloud_provision() worker automatically reconciles them:

  • If the account has no email on record (e.g. legacy local account), a deterministic synthetic email is generated: username@motormeasure.app.
  • The worker tests reachability. If offline, it defers provisioning without disrupting the user.
  • If online, it signs into Supabase Auth. If the cloud account does not yet exist, it calls sign_up() and injects user profile metadata into the cloud database.
  • Once authenticated, it retrieves the server-authoritative role from profiles.role and updates the local SQLite mirror if required.

4. Password Recovery & OTP Flow

When an authenticated account loses its password:

  1. The clinician enters their email on the login screen and clicks "Forgot Password".
  2. AuthService.request_password_reset(email) calls Supabase's reset_password_for_email(), sending an OTP recovery code to the registered inbox.
  3. The user inputs the 6-digit OTP token and a new password.
  4. AuthService.complete_password_reset(page, email, token, new_password) validates the token via verify_otp(type="recovery"), updates the cloud password, and immediately re-hashes and mirrors the new password into local SQLite.
